## What this project demonstrates
An end-to-end analytics build: a documented data contract, defensive data cleaning with full audit trails,
approved KPI formulas, a reconciliation/data-quality layer, and a 9-page bilingual executive dashboard - the
kind of system built for a real finance/accounting function, running here entirely on synthetic demonstration
data (2022-2025).

## Dashboard Pages
1. Executive Overview / الملخص التنفيذي
2. Sales Performance / أداء المبيعات
3. Purchasing Performance / أداء المشتريات (Internal vs External purchases kept as clearly separate measures)
4. Returns Analysis / تحليل المرتجعات
5. VAT Analysis / تحليل ضريبة القيمة المضافة (indicative/analytical only - see "Accounting Assumptions" below)
6. Customers & Suppliers / العملاء والموردون
7. Year-over-Year Analysis / المقارنة السنوية
8. Supplier Balances / أرصدة الموردين
9. Data Quality & Reconciliation / جودة البيانات والمطابقة

## Data Model
Star-schema style: `DimDate`, `DimCustomer`, `DimSupplier` (with `in_local`/`in_foreign` flags keeping the
Internal and External supplier universes cleanly separate), `DimCostCenter`. Facts: `FactSales`,
`FactSalesReturns`, `FactLocalPurchases` (Internal), `FactForeignPurchases` (External),
`FactLocalPurchaseReturns`, `FactProfit`, `FactSupplierDebt`, `FactSupplierCreditors` - all at
row-transaction grain. The synthetic
workbook (`data/sample_financial_data.xlsx`) reproduces the same 8-sheet structure, including one embedded
grand-total row per transactional sheet, so the Data Quality page's reconciliation logic has real (synthetic)
structural rows to exercise.

## Accounting Assumptions (do not change without re-reading this)
- **Profit is a supplied, authoritative input** - read directly from a dedicated Profit sheet/dataset and
  displayed as-is. It is **never** calculated in this project as `Sales − Purchases`, and Purchases are never
  treated as Cost of Goods Sold. No Gross Profit, Net Margin, Operating Profit, EBIT, or EBITDA is derived
  anywhere.
- **Internal vs External Purchases are kept independent** everywhere, each with its own supplier universe -
  never combined into one generic "Purchases" figure without showing both components. Total Purchases =
  Internal Purchases (before VAT) + External Purchase Total (including additional cost); this is a sum of two
  VAT-exclusive bases, never netted against Purchase Returns.
- **External Purchases have no VAT field** in the schema (import/LC-style purchases) - no VAT is invented for
  them.
- **Purchase Returns are not linked to a supplier** - the schema has no reliable supplier relationship for
  returns, so none is fabricated; Purchase Returns are analyzed by Cost Center instead.
- **Supplier Balances are a separate, static, point-in-time snapshot concept** - not derived from purchase
  transactions, and debt/creditor totals are shown separately, never netted into one position.
- **VAT figures are analytical/indicative only** - based on the transaction data available, and are not
  presented as, and must never be treated as, an official VAT filing.
- **Transaction counts are row counts**, not unique-invoice counts (a documented, intentional data-contract
  choice - see `src/data_cleaning.py`).

## Synthetic Data
Generated by `scripts/generate_synthetic_data.py` (fixed random seed, fully reproducible, zero external
input). Approximate scale: ~15,000 Sales transactions, ~950 Sales Returns, ~2,800 Internal Purchases, ~800
External Purchases, ~380 Internal Purchase Returns, 220 fictional named customers (plus one generic cash/
walk-in bucket), ~30 fictional Internal Suppliers, ~16 fictional External Suppliers (the two supplier lists
are verified disjoint), 6 public-safe Cost Center names, and independently-sampled annual Profit and Supplier
Balance figures for 2022-2025. All names are built from fixed templates + counters - never a name-corpus
library, so there is no possibility of coincidentally reproducing a real business's identity. See the
generator's own docstring for the full design.

## How to Run
```
git clone <this-repo>
cd executive-financial-dashboard-public
pip install -r requirements.txt
python scripts/generate_synthetic_data.py   # creates data/sample_financial_data.xlsx
streamlit run app.py
```
Then open the Local URL Streamlit prints (typically `http://localhost:8501`). No environment variables, no
external accounts, and no private file paths are required - the workbook path is resolved relative to the
project root.

## Arabic / English Support
Every user-visible string comes from a single translation dictionary (`src/translations.py`,
`t(key, lang)`). One analytical layer feeds both languages - no duplicated business logic. RTL is applied via
the CSS `direction` property plus CSS logical properties throughout `assets/styles.css`. The sidebar's
Year/Quarter/Customer/Internal Supplier/External Supplier/Cost Center filter selections persist correctly
across a language toggle and across page navigation.

## Known Limitations
- Local Purchase Returns cannot be attributed to a supplier or a specific original purchase transaction, and
  are never subtracted from External Purchases.
- Sales-Return-to-original-sale linkage is best-effort/illustrative only, never used to aggregate monetary
  totals.
- Supplier Debt and Supplier Creditor totals are shown separately, not netted.
- Working Days modeling excludes Fridays and two configurable Eid holiday blocks per year; other public
  holidays are not modeled.
- RTL support is CSS-based (Streamlit has no first-party RTL API); native widget chrome may not mirror
  perfectly even though all text, layout direction, and reading order do.
